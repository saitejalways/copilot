# GitHub Copilot Instructions - TPR API

> **Core rules, architecture overview, and critical business rules are defined in [`AGENTS.md`](../AGENTS.md) at the repository root.** This file extends those rules with detailed patterns, code examples, and workflow guidance. When a rule appears in both files, AGENTS.md is authoritative.

## Application Domain and Context

### What is this Application?

This is the **Third-Party Regulatory (TPR) API** - a critical component of ACA Group's unified platform for **financial regulatory compliance and investor management**. The primary focus is the **Anti-Money Laundering (AML) and Know Your Customer (KYC)** module.

### Core Purpose

The AML/KYC module is an advanced CRM platform with specialized features for:

- **Screening Management**: Performing automated and AI-assisted screenings of prospective investors (individuals and businesses)
- **Investor Onboarding**: Managing the full lifecycle of investor registration and compliance verification
- **Risk Detection**: Identifying and alerting analysts to Items of Interest (IoIs) and compliance red flags
- **Analyst Workflow**: Providing a structured workflow for analysts to review AI-generated suggestions and make compliance decisions

### Key Business Concepts

**Investors**: Both individuals and businesses that are prospective investors, tracked through the system for ongoing compliance monitoring.

**Screenings**:

- One-time screenings: Single evaluation against regulatory databases
- Continuous screenings: Ongoing periodic evaluations to catch changes in investor status
- Can be triggered on onboarding or scheduled for recurring evaluation

**AI Screening Results**:

- Generated by AI-assisted screening engines (adverse media, PEP/sanctions, etc.)
- Treated as **suggestions, not decisions** - analysts must review and accept/reject
- Match results indicate potential compliance issues that need investigation
- Non-match results are negative findings that clear the investor

**Items of Interest (IoIs)**: Alerts generated when screenings identify potential issues requiring analyst attention.

**Analyst Workflow**: Analysts review flagged items, investigate, and make final compliance decisions (accept risk or escalate).

### Technical Architecture

This API repository contains:

- **REST APIs**: Endpoints for investor management, screening operations, results review, and alerting
- **Event System**: Event publishers and listeners for async processing of screenings and notifications
- **SignalR Integration**: Real-time notifications to analysts when new IoIs are detected
- **Background Jobs (Hangfire)**: Async processing for screenings, event publishing, and continuous evaluation

### Critical Business Rules

1. **Never hard delete investor or screening data** - maintain complete audit trail
2. **Always soft delete** with timestamps and user tracking for compliance purposes
3. **Events are critical** - all write operations must publish events for audit and system integration
4. **AI is advisory** - results are suggestions pending analyst decision
5. **Real-time notifications** - analysts must be immediately notified of new IoIs
6. **Client isolation** - each client's data must be strictly isolated (multi-tenant system)
7. **Regulatory compliance** - all rules, tests, and data handling must consider compliance requirements

**Remember**: This is a compliance system. Code quality, test coverage, and audit trails are not optional - they're regulatory requirements.

## Logging Standards

As a feature is developed, provide available and comprehensive logging. Logging is essential for diagnosing issues, tracing process flow, and monitoring system health.

### Log Levels

- **Debug**: Messages only useful for debugging purposes, not for tracing normal process flow
- **Info**: Messages useful for tracing the general flow of a process
- **Warning**: Something unexpected happened, but not an error condition
- **Error**: A critical exception was thrown — always include the exception object

### Logging Best Practices

1. **Include relevant data** as structured log properties — use `{PropertyName}` placeholders, not string interpolation:

```csharp
// ✅ GOOD
logger.LogInformation(
    "Investor screening completed. ScreeningId: {ScreeningId}, InvestorId: {InvestorId}, MatchCount: {MatchCount}, Duration: {DurationMs}ms",
    screeningId, investorId, matches.Count, stopwatch.ElapsedMilliseconds);

// ❌ BAD
logger.LogInformation($"Investor screening completed for {investorId}");
```

2. **Use stopwatches for performance-sensitive operations**:

```csharp
var stopwatch = Stopwatch.StartNew();
var results = await _screeningEngine.ExecuteScreeningAsync(investor);
stopwatch.Stop();

logger.LogInformation(
    "Screening engine completed in {DurationMs}ms for InvestorId: {InvestorId}",
    stopwatch.ElapsedMilliseconds, investorId);
```

3. **Log both success and failure paths**:

```csharp
if (result is null)
{
    logger.LogWarning(
        "No screening result found for ScreeningId: {ScreeningId}, ClientId: {ClientId}",
        screeningId, clientId);
    return null;
}

logger.LogInformation(
    "Screening result retrieved for ScreeningId: {ScreeningId}, Status: {Status}",
    screeningId, result.Status);
```

4. **Log exceptions with context** — always pass the exception as the first argument:

```csharp
catch (Exception ex)
{
    logger.LogError(
        ex,
        "Failed to save screening changes for ScreeningId: {ScreeningId}, InvestorId: {InvestorId}",
        screeningId, investorId);
    throw;
}
```

5. **Log important business decisions and state transitions**:

```csharp
logger.LogInformation(
    "Risk rating updated for InvestorId: {InvestorId}, PreviousRating: {PreviousRating}, NewRating: {NewRating}",
    investorId, previousRating, newRating);
```

## Code Stewardship

As you develop features, be a good steward of the codebase:

- **Improve code style and formatting** in files you touch: fix indentation, spacing, and style issues in existing code as you work
- **Perform small refactors** to improve clarity: extract magic strings to constants, rename unclear variables, simplify complex conditionals
- **Avoid major refactors**: don't overhaul entire files or systems unless explicitly requested; keep changes focused on the feature
- **Leave the code better than you found it**: small improvements compound

```csharp
// While working on a feature, improve code you touch:

// ❌ Unclear naming and poor formatting
public async Task ProcessAsync(Guid id)
{
	var x = await _context.Investor.FindAsync(id);
	if(x!=null&&!x.deleted) { x.status = "processed"; await _context.SaveChangesAsync(); }
}

// ✅ Clear naming and proper formatting
public async Task ProcessInvestorScreeningAsync(Guid investorId)
{
	var investor = await _context.Investor.FindAsync(investorId);
	if (investor is null || investor.IsDeleted)
	{
		return;
	}

	investor.Status = "Processed";
	await _context.SaveChangesAsync();
}
```

**When NOT to refactor**: don't touch unrelated code unless it's a trivial fix (rename, formatting).

## Never Nest Conditionals — Always Use Early Returns

Nested conditionals are never acceptable when guard clauses would work. Guards at the top, happy path at the bottom.

```csharp
// ❌ Nested if/else
public async Task<Result<Entity>> GetEntityAsync(Guid id)
{
    var entity = await _context.Entity.FindAsync(id);
    if (entity is not null)
    {
        if (!entity.IsDeleted)
        {
            if (entity.ClientId == Principal.ClientId)
                return Result<Entity>.Success(entity);
            else
                return Result<Entity>.Failure("Access denied");
        }
        else
            return Result<Entity>.Failure("Entity is deleted");
    }
    else
        return Result<Entity>.Failure("Entity not found");
}

// ✅ Early returns — linear flow
public async Task<Result<Entity>> GetEntityAsync(Guid id)
{
    var entity = await _context.Entity.FindAsync(id);

    if (entity is null)
        return Result<Entity>.Failure("Entity not found");

    if (entity.IsDeleted)
        return Result<Entity>.Failure("Entity is deleted");

    if (entity.ClientId != Principal.ClientId)
        return Result<Entity>.Failure("Access denied");

    return Result<Entity>.Success(entity);
}
```
